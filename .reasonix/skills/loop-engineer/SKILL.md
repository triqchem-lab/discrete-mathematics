# loop-engineer：通用自主迭代修复工程师

你是通用的 Loop Engineering 执行引擎。职责是自主完成"**计划 → 执行 → 观察 → 反思 → 调整**"认知闭环，直到任务闭合或到达阻塞边界。

本技能只定义**迭代修复的元规则**。所有领域特定的错误模式、修复食谱、决策树，均存储在**附录（Appendices）**中。

---

## 一、核心认知循环

```
┌─────────────────────────────────────────────────────────────────────┐
│                        1. 目标锚定（Plan）                         │
│  明确最终目标 + 识别硬约束（时间预算、依赖范围、禁止的修改类型）   │
└─────────────────────────────┬───────────────────────────────────────┘
                              ▼
┌─────────────────────────────────────────────────────────────────────┐
│                    2. 预检防火墙（Pre-flight）                      │
│  快速扫描目标上下文，标记已知高风险项（见附录"预检清单"）          │
│  预检不通过 → 输出 PREFLIGHT_BLOCKED，不进入循环                  │
└─────────────────────────────┬───────────────────────────────────────┘
                              ▼
┌─────────────────────────────────────────────────────────────────────┐
│                   3. 执行-诊断-修复-验证（Act-Observe-Refine）     │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌────────────┐  │
│  │ 执行动作  │ → │ 收集反馈  │ → │ 索引附录  │ → │ 应用修复   │  │
│  │ (修改/运行)│   │ (错误/日志)│   │ (匹配模式)│   │ (最小改动) │  │
│  └──────────┘    └──────────┘    └──────────┘    └────────────┘  │
│        ↑                                           │              │
│        └─────────── 若失败，循环（≤12次）────────────┘              │
│                   每次迭代必须更换修复维度                         │
└─────────────────────────────┬───────────────────────────────────────┘
                              ▼
┌─────────────────────────────────────────────────────────────────────┐
│                4. 回归冲击波检测（Regression Scan）                 │
│  本次修改是否可能影响依赖方？→ 运行最小回归测试集                  │
│  依赖方被破坏 → 启动子循环修复依赖方（不计入主循环次数）           │
└─────────────────────────────┬───────────────────────────────────────┘
                              ▼
┌─────────────────────────────────────────────────────────────────────┐
│                    5. 能耗计量（Energy Budget）                    │
│  记录耗时/资源占用。超出预算红线 → 强制进入性能急救                │
└─────────────────────────────┬───────────────────────────────────────┘
                              ▼
┌─────────────────────────────────────────────────────────────────────┐
│              6. 闭合（Close）或 升级（Escalate）                   │
│  成功 → 输出 DONE + 持久化失败指纹（更新附录）                     │
│  失败且超出循环上限 → 输出 BLOCKED + 完整诊断链                    │
│  遇到认知外错误 → 输出 ESCALATION_REQUIRED + 原始证据              │
└─────────────────────────────────────────────────────────────────────┘
```

## 二、通用循环协议（硬性规则）

### 2.1 迭代上限
- **主循环上限：12 次**。超过 5 次仍未通过，强制标记 `BLOCKED`，禁止无限重试。
- **回归子循环上限：3 次**。超过则回滚当前修改，标记 `REGRESSION_CRITICAL`。

### 2.2 迭代不重复原则（反原地打转）
- **第 1 次失败** → 尝试"低侵入性"修复（如补全依赖、调整参数）。
- **第 2 次失败**（同一问题）→ 切换维度（如从"补导入"切到"改架构"，或从"改代码"切到"改编译选项"）。
- **第 3 次失败** → 检查是否存在"隐式上下文污染"（如全局 flag 传染、环境变量干扰）。
- **第 4 次失败** → 将复杂证明/过程拆解为独立原子单元，破坏联合归一化/联合编译。
- **第 5 次失败** → 尝试深度重构（如类型层级调整、模块拆分）。
- **第 6-8 次失败** → 检查跨模块级联效应，逐级分离依赖。
- **第 9-12 次失败** → 放弃自动修复，输出完整诊断链。

**绝对禁止**：连续两次使用完全相同的修复动作（即重复执行无效命令）。

### 2.3 模式置信度分流（认知外处理）
遇到错误反馈后，先执行置信度评估：

| 置信度 | 判定标准 | 动作 |
|--------|----------|------|
| **高（≥90%）** | 错误指纹与附录中的某个模式完全匹配 | 直接应用对应修复食谱 |
| **中（50%-90%）** | 部分匹配，但有未知变量/堆栈差异 | 生成 2~3 个候选修复，按"侵入性从低到高"排序，依次尝试 |
| **低（<50%）** | 错误信息在附录中无对应项，或包含 `Internal Error` / `Fatal` | **立即中止循环**，输出 `ESCALATION_REQUIRED`，不浪费迭代 |

### 2.4 回归冲击波强制扫描
当修复涉及以下"敏感区域"时，必须触发回归测试：
- 公共基础库（如标准库、核心类型定义）
- 编译选项（`OPTIONS`、`CFLAGS`、环境变量）
- 构建脚本（`Makefile`、`Cargo.toml`、`package.json`）

触发后，运行约定的最小回归测试集。若发现新破坏，启动子循环修复，上限 3 次。

### 2.5 能耗与性能预算
- **绿区**：执行时间 < 30s → 正常推进。
- **黄区**：30s ≤ 执行时间 < 120s → 发出性能警告。
- **红区**：执行时间 ≥ 120s → 强制进入"性能急救模式"：拆解大块逻辑、分离联合编译单元。若 3 分钟内无法优化，标记 `BLOCKED (PERFORMANCE)`。

## 三、输出格式（通用）

```markdown
状态: DONE | BLOCKED | ESCALATION_REQUIRED | PREFLIGHT_BLOCKED
任务目标: [一句话描述]
迭代次数: [实际循环次数]
最终动作: [最后一次成功的修改，或最后一次失败的动作]
模式匹配: [高/中/低] — [匹配的附录条目，若无则写"无匹配"]
回归测试: [通过 / 发现 X 个新问题已修复 / 发现 X 个新问题未修复]
能耗: [耗时] — [绿/黄/红]
失败指纹（仅 BLOCKED 时）:
  [1] 错误类型 → 尝试修复 → 结果
  [2] ...
  [N] 最终诊断：[根因分析]
```

## 四、附录机制（可插拔知识库）

本技能本身**不包含**任何领域特定知识。所有领域知识以"附录"形式挂载。

### 附录编写规范
```markdown
## 附录 X：[领域名称] 专项知识库
### X.1 预检清单
### X.2 错误指纹与修复食谱
### X.3 性能陷阱
### X.4 回归测试命令
```

### 引擎消费附录的方式
1. **预检阶段**：扫描所有附录的"预检清单"。
2. **诊断阶段**：提取错误指纹，在所有附录中全文匹配。
3. **修复阶段**：匹配后执行对应修复动作。
4. **性能阶段**：查询"性能陷阱"表。

## 五、通用核心原则

1. **闭环优于单次尝试**：能自动迭代就不手动猜测。
2. **诊断优先于修改**：索引附录的时间永远小于盲改后重跑的等待时间。
3. **失败历史是资产**：每次 `BLOCKED` 输出都应作为补充语料，用于后续更新附录规则。
4. **侵入性最小优先**：同一问题有多个解法时，优先选择改动范围最小的那个。
5. **人类可读性优先**：AI 可以暴力重试，但输出给人类的诊断链必须清晰可理解。

## 附录 A：Agda / 大衍 形式化证明专项知识库

> 本附录由 proof-engineer 技能的知识迁移而来。

### A.1 预检清单
- [ ] 文件头是否有 `{-# OPTIONS --rewriting --guardedness #-}`？
- [ ] 是否导入 `Cubical.Foundations.Prelude` 但未声明 `--cubical`？
- [ ] 是否有 `postulate ... where ...` 语法反模式？
- [ ] 是否有 `data X` 嵌套在 `record ... where` 内？

### A.2 六类错误指纹与修复食谱

| 类 | 指纹 | 根因 | 修复 |
|----|------|------|------|
| **A** | `NotInScope` for stdlib符号 | stdlib 2.4 opt-in 导出 | 补 `using`，如 `open import Data.Bool using (Bool; true; false)` |
| **B** | `NotInScope` for Sovereign符号 | 模块路径不存在 | 查正确路径；常见：`RootMath.Base`→`Base.Trit` |
| **C** | `AmbiguousName` for `_+_`/`zero`/`suc` | 多模块同名构造子 | `Data.Integer` renaming `_+_` to `_+ℤ_`；`Data.Fin` renaming `zero` to `fzero` |
| **D** | `InfectiveImport` / `SafeFlagPragma` | `--rewriting` vs `--safe` | 文件头保留 `--rewriting`，命令行不加 |
| **E** | `ParseError` for `postulate...where` | 语法非法 | 分离为独立 `postulate` 块 |
| **F** | `UnequalTypes` / `Set` vs `Set₁` | 大数据类型层级 | `Set → Set₁` |

### A.3 特定符号迁移表

| 旧路径 (无效) | 新路径 (有效) |
|---------------|---------------|
| `Sovereign.RootMath.Base` | `Sovereign.Base.Trit` |
| `Data.Empty.¬_` | `Relation.Nullary.Negation.¬_` |
| `Data.Nat.Properties.¬suc≤zero` | **stdlib 2.4 不存在** → 本地定义 |
| `Data.List._∈_` | `Data.List.Membership.Propositional._∈_` |
| `Data.X.Y.Trust` (非法标识符) | `dataXyTrust` (camelCase) |
| `module_name` (关键字冲突) | `modName` |

### A.4 性能陷阱
| 场景 | 症状 | 优化策略 |
|------|------|----------|
| 大 Fin 递归 | `Heap exhausted` / 编译超时 | 引用已编译模块，不重新定义 |
| `mod-helper` 展开 | `UnsolvedConstraints` | 添加 `REWRITE` 规则 |
