## 二、本库为什么用「六层」——当时的判据（文档原文，非我推测）

`docs/migration/五层架构文档.md` §一 给出**依赖方向轴**：

```
Application   (L4) 应用：Morse/Hodge/Burau-KM/Postnikov/NSE/BSD/YM/Problem 全族
    ↓（单向：高层 import 低层，反向 = 错位）
Synthesis     (L3) 合成：CRT 波系统/Hensel 调度/FAb 商/HIT 商/分水岭定理/表示论桥
    ↓
Algebra       (L2) 结构：GF(3^k) 域塔/Laurent 两路线/群与表示/Hensel 塔代数面
    ↓
Base          (L1) 基座：Trit(⊕,⊗)/FAb 群律/SunyiBase/IntArith/Fin3/算术基础件
    ↓
Foundation    (L0) 公理：GF(3) 公理/数字根/损益/归零/离散存在/元数学红线
——————————————————————————————————————————
Infrastructure 跨切带：Engine/Trust/AI/Verify/审计聚合/宪法审查——豁免单向律
```

**定层判据三条**（§三）：① 目录默认表；② 重点面逐件细分（Analysis 42 件逐件、Cubical 3 件 → Base）；
③ **import 图单调性**：`A import B ⇒ 层(A) ≥ 层(B)`；④ 违者入「错位清单」（只报不改）。

**跨切豁免带**（§五，v2 新增）：横切/审计/宪法类模块不参与单调性判据，归 `Infrastructure`；
入带判据三问（职责横向？import 覆盖 ≥3 层？单点优于拆分？）；带内互相 import 自由；新成员须 journal 记录。

**结案成果**（`docs/migration/README.md`）：**803/803 覆盖、474 件移动 100%、断链 0、循环 0、结构 lint 0/0**。

**⇒ 为什么选层轴而不是概念轴（这就是答案）**：
本库是**证明库**，Agda 无循环 import —— **编译顺序与依赖单调性是硬约束**。
层轴让它**可机检**：一个脚本就能列出所有违反 `层(A) ≥ 层(B)` 的边（当时列出 158 条错位）。
概念轴做不到这一点：`group-theory` 可以 import `ring-theory`，反过来也可以，**没有可判定的规则**。

## 三、三库对照：轴的选择与代价

| 维度 | unimath | stdlib | 本库（六层） |
|---|---|---|---|
| 主轴 | 数学概念 + 两层基底 | 数学概念/语言机制 | **依赖方向（层）** |
| 能否机检依赖方向 | ❌（无层规则） | ❌ | ✅ **判据 = `层(A) ≥ 层(B)`** |
| 检索/叙述友好度 | ✅ 强（按学科找） | ✅ 强 | ⚠ 弱（`Application` 304 平铺）|
| 典型反模式 | — | — | **层内不细分 = 倾倒场** |
| 目录名风格 | 小写 kebab-case 长概念名 | PascalCase 概念 | PascalCase 层名 |

**结论：六层本身是合理的、且有据可依**——它编码的是**编译顺序与依赖纪律**，这是证明库的刚需，
不是随意分层（474 件移动、0 循环、0 断链是它的验收证据）。

**真正的缺陷只有一个：层内没有概念细分。** 实测平铺情况：

| 层 | 总数 | 直属（平铺） | 子目录 |
|---|---|---|---|

| `Algebra` | 277 | 200 | GroupTheory 27 / Jacobian 14 / Holographic 12 / … |
| `Synthesis` | 168 | 159 | Graphs 8 / DiscreteCubical 1 |
| `Foundation` | 31 | 27 | Finiteness 4 |

## 四、推荐：**层轴（骨架）不动 + 层内加概念子目录**（= unimath 的两轴叠加）

unimath 已经证明这条路可行：`foundation-core` → `foundation` → 学科目录。
本库对应做法：

```
Foundation/            （L0，保持）
Base/                  （L1，保持）
Algebra/               （L2）
  ├─ FieldTower/       GF(3)/GF(9)/GF(27)/GF(81)/GF(243)/GF(729)
  ├─ GroupTheory/      已有
  ├─ RingTheory/ Laurent、R₁₂、Doz
  ├─ Presentation/     八要素 record + DC 实例
  ├─ Combinatorics/    Burnside、幻方、T6 格点
  └─ NumberTheory/     数字根、CRT 算术
Synthesis/             （L3）
  ├─ Homotopy/         AStep/AHomotopy/πₙᵈ/π₁bt/分水岭
  ├─ CRT/              波系统、Hensel、FAb 商、HIT 商
  └─ Representation/   A₄ 表示、Burau
Application/           （L4）
  ├─ Problems/         Kakeya / ABC / FLT / NS / YM / PvsNP / RH 的判据与诊断
  ├─ Morse/  Hodge/  Packet/  Physics/  ML/
Infrastructure/        （跨切带，保持）
```

**为什么不取消 `Application`/`Synthesis`**：它们编码「用在哪 / 怎么合成」，正是**判据层**（壁垒定理、三重完备性、
分水岭）的驻地——取消它们等于把"判据即对象"的那批件打散回各学科，反而更乱。
**但 `Application` 必须至少拆成 `Problems/` + 若干专题**，否则 304 平铺无法维护。

## 五、成本与执行序（诚实）

**Agda 硬约束：目录 = 模块命名空间** ⇒ 任何移动都改模块名 + 全部 import。

| 阶段 | 内容 | 风险 | 备注 |
|---|---|---|---|
| 0 | 改 `AGENTS.md` Architecture 段（512→823、旧目录→9 个）+ 本文件作为分类规范 | 零 | 不碰 `.agda` |
| 1 | `Application/` 拆 `Problems/` + 专题（304 件里最痛的部分） | 中 | 分批，每批全量编译 |
| 2 | `Algebra/`/`Synthesis/` 层内概念细分 | 中 | 同上 |
| 3 | 若仍要彻底对齐 unimath：把层名换成学科名 | 高 | 需重做依赖单调性检查（层轴没了就失去机检） |

**我的建议**：做 0 与 1，**不做 3**——因为层轴是本库**唯一可机检的依赖纪律**，丢掉它换来的是"更好看"，代价是"错位无法自动发现"。
